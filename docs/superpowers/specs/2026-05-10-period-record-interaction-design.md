# 经期开始/结束记录交互设计

## 背景

当前首页已经合并了状态摘要、月历浏览和经期记录能力，但“开始记录”“选择结束日期”“编辑已有记录”共存于同一页面，用户需要自行理解当前所处步骤，首次使用时心智负担偏高。

现有问题主要集中在以下几个方面：

- 同一个日历点击，在不同状态下承载不同含义，步骤感不明确。
- 开始日期一旦选定，界面没有持续强化展示，用户需要依赖记忆完成第二步。
- 日期点击后的结果反馈主要位于页面下方，和实际点击位置距离较远。
- 新增记录与编辑记录的规则和状态表达不完全一致，影响用户建立稳定心智。

本次设计只优化“经期开始日期 / 结束日期记录”这一核心交互，不新增额外健康指标，不改动数据库结构，不改变预测算法。

## 目标

- 让用户第一次使用时就能理解开始记录和结束记录的流程。
- 把记录流程收敛为显式两步，避免隐藏状态依赖记忆。
- 在保存前持续展示区间预览，降低误操作率。
- 让新增记录和编辑记录尽量遵循一致的交互规则。
- 保持现有首页信息结构，不引入新的独立页面或复杂向导。

## 非目标

- 不新增流量、痛经、心情、好习惯等附加指标。
- 不引入多页面 wizard 或全屏弹层流程。
- 不调整首页顶部摘要卡片的信息内容。
- 不处理云同步、账号体系、远程接口等能力。

## 设计原则

### 1. 当前任务必须可见

用户任何时刻都应明确知道自己正在执行的是：

- 选择开始日期
- 选择结束日期
- 查看已有记录
- 编辑已有记录

界面不能依赖用户记忆当前状态。

### 2. 同一时间只保留一个主动作

记录区面板在任一状态下只提供一个最主要的确认动作，避免多个同级按钮同时争夺注意力。

### 3. 关键上下文持续展示

一旦用户开始记录，已选开始日期、当前结束日期、即将保存的区间需要持续可见，直到流程完成或取消。

### 4. 新增与编辑规则统一

新增记录和编辑记录都允许用户反向选择日期，系统统一按时间先后自动整理为合法区间，避免同一业务对象出现两套规则。

### 5. 中断操作必须明确确认

用户在新增或编辑过程中离开当前流程时，不能静默丢失已选内容，必须有明确确认。

## 页面结构

页面继续保持当前三段式结构：

1. 顶部摘要区：展示今天、最近记录、预测信息。
2. 月历区：负责日期浏览和选择。
3. 记录区面板：负责查看、开始记录、结束记录、编辑和删除。

本次调整的重点是第三部分“记录区面板”的状态表达，以及它与月历点击行为的联动规则。

## 核心状态设计

### 状态 1：默认态

进入条件：

- 当前没有未完成的开始日期。
- 当前选中日期不属于已有记录。

记录区面板展示：

- 标题：`记录经期`
- 说明：`已选日期：{date}`
- 辅助文案：`点击下方按钮，将这一天设为经期开始日期`
- 主按钮：`设为开始日期`

交互规则：

- 用户点击月历任意日期，只更新“已选日期”。
- 点击主按钮后，写入本地状态 `pendingStartDate = selectedDate`。
- 此时不写数据库，直接进入“结束日期选择态”。

设计意图：

- 用明确的动作文案替代抽象的“开始记录”。
- 让用户把当前动作理解为“把这一天设成开始日期”，而不是进入某个隐式模式。

### 状态 2：结束日期选择态

进入条件：

- 已存在 `pendingStartDate`，表示开始日期已经确认。

记录区面板展示：

- 标题：`请选择结束日期`
- 说明一：`已选开始日期：{startDate}`
- 说明二：`当前结束日期：{endDate}`
- 区间预览：`将记录为：{rangeStart} - {rangeEnd}`
- 主按钮：`设为结束日期`
- 次按钮：`重新选开始日期`
- 次按钮：`取消本次记录`

交互规则：

- 用户点击月历任意日期，只更新当前结束日期候选值。
- 系统实时根据 `pendingStartDate` 和 `selectedDate` 计算排序后的区间预览。
- 点击 `设为结束日期` 时执行保存。
- 点击 `重新选开始日期` 时，将当前选中日期设为新的开始日期，并保留在本状态。
- 点击 `取消本次记录` 时，清空 `pendingStartDate`，回到默认态。

设计意图：

- 让开始日期、结束日期和最终结果在保存前全部可见。
- 降低“我现在到底在做什么”的不确定感。

### 状态 3：已有记录查看态

进入条件：

- 当前选中日期属于某条已有经期记录。

记录区面板展示：

- 标题：`已记录经期`
- 说明：`记录区间：{startDate} - {endDate}`
- 辅助文案：`当前日期属于这段经期`
- 主按钮：`编辑记录`
- 危险按钮：`删除记录`

交互规则：

- 点击 `编辑记录` 进入编辑态。
- 点击 `删除记录` 触发二次确认弹窗。
- 在存在未完成记录流程时，如果用户点击到已有记录日期，不直接切换到本状态，先弹出确认。

设计意图：

- 已有记录优先于新增记录逻辑展示，防止语义冲突。

### 状态 4：编辑态

进入条件：

- 用户在已有记录查看态点击 `编辑记录`。

记录区面板展示：

- 标题：`编辑经期记录`
- 字段一：`开始日期：{startDate}`
- 字段二：`结束日期：{endDate}`
- 辅助文案：`正在编辑：开始日期` 或 `正在编辑：结束日期`
- 区间预览：`当前记录区间：{rangeStart} - {rangeEnd}`
- 主按钮：`保存修改`
- 次按钮：`取消编辑`

交互规则：

- 面板中始终标明当前正在编辑哪个字段。
- 点击月历日期时，只更新当前正在编辑的字段。
- 允许用户反向选择日期，保存前统一排序。
- 保存成功后回到已有记录查看态。

设计意图：

- 把编辑态与新增态统一为“选日期 + 看区间 + 确认保存”的同一类交互模型。

### 状态 5：保存中

进入条件：

- 新增保存中
- 编辑保存中
- 删除执行中

记录区面板规则：

- 标题沿用当前状态标题。
- 主按钮文案变为：`保存中...` 或 `删除中...`
- 所有相关交互禁用：日期点击、月份切换、回今天、按钮点击。

设计意图：

- 给出明确等待反馈，避免保存过程中上下文被切走。

### 状态 6：放弃确认态

进入条件：

- 新增流程中途尝试离开当前流程。
- 编辑过程中尝试切换日期、月份、返回今天、切换 Tab 或进入其它记录。

提示文案：

- `当前操作尚未完成，放弃后本次选择将丢失`

按钮：

- `确认放弃`
- `继续当前操作`

设计意图：

- 避免用户在无感知的情况下丢失输入内容。

## 日历交互规则

### 默认态

- 点击日期：更新当前选中日期。
- 不触发保存，不切换到编辑态。

### 结束日期选择态

- 点击日期：更新当前结束日期候选值。
- 如果和开始日期形成重叠区间，面板内即时提示错误，不等到保存时才提示。

### 已有记录查看态

- 点击其它已有记录日期：切换到对应记录查看态。
- 点击空白日期：进入默认态。

### 编辑态

- 点击日期：更新当前编辑字段。
- 不允许静默退出编辑。

## 月份切换与回今天规则

### 默认态

- 允许自由切换月份。
- 允许点击 `回今天`。

### 结束日期选择态

- 允许切换月份和点击 `回今天`。
- 但 `已选开始日期` 和区间预览必须始终可见。

### 编辑态

- 若切月或回今天不会退出编辑态，则允许。
- 若当前交互实现会导致退出编辑态，则必须先弹放弃确认。

### 保存中

- 一律禁止切月和回今天。

## 规则统一

### 日期顺序规则

- 新增记录允许开始日期晚于结束日期。
- 编辑记录也允许开始日期晚于结束日期。
- 系统在展示区间预览和保存时统一自动排序：
  - `rangeStart = min(startDate, endDate)`
  - `rangeEnd = max(startDate, endDate)`

### 重叠校验规则

- 新增记录和编辑记录都需要执行重叠校验。
- 校验尽量前置到日期选择后即时执行，而不是等用户点击保存后再报错。
- 编辑当前记录时，校验需要排除自身记录。

### 中断规则

- 新增中断：必须确认。
- 编辑中断：必须确认。
- 保存中断：不允许。

## 错误与反馈设计

### 成功反馈

- 设为开始日期：不弹窗，直接切换到结束日期选择态即可。
- 保存成功：展示轻提示 `经期记录已保存`，并刷新月历标记和详情。
- 删除成功：展示轻提示 `经期记录已删除`，并刷新界面。

### 错误反馈

- 日期区间重叠：面板内错误文案 `该日期区间与已有记录重叠，请重新选择`
- 数据加载失败：保留现有提示，但应尽量补充页面内状态说明。
- 保存失败：优先在面板内展示错误文案，并保留当前状态方便用户重试。
- 删除失败：提示失败原因，并保持当前记录查看态。

设计要求：

- 错误尽量贴近当前操作位置，不只依赖系统弹窗。
- 写入失败和刷新失败要分开反馈，避免用户误以为数据完全未保存。

## 典型用户路径

### 路径 1：新增一条经期记录

1. 用户点击某个空白日期。
2. 记录区显示 `已选日期` 和按钮 `设为开始日期`。
3. 用户点击 `设为开始日期`。
4. 面板进入结束日期选择态，持续展示 `已选开始日期`。
5. 用户点击另一个日期作为结束日期。
6. 面板实时显示 `将记录为：开始 - 结束`。
7. 用户点击 `设为结束日期`。
8. 保存成功后回到默认态，并刷新月历标记。

### 路径 2：重新选择开始日期

1. 用户已经处于结束日期选择态。
2. 发现开始日期选错。
3. 点击 `重新选开始日期`。
4. 当前选中日期替换原开始日期。
5. 面板继续停留在结束日期选择态，等待选择新的结束日期。

### 路径 3：取消新增流程

1. 用户处于结束日期选择态。
2. 点击 `取消本次记录`。
3. 清空未完成的开始日期。
4. 返回默认态。

### 路径 4：编辑已有记录

1. 用户点击某个已有记录日期。
2. 面板显示已有记录查看态。
3. 用户点击 `编辑记录`。
4. 进入编辑态，默认聚焦开始日期或最近被修改字段。
5. 用户通过月历改动日期。
6. 面板实时显示新的区间预览。
7. 用户点击 `保存修改`。
8. 保存成功后回到已有记录查看态。

## 验收标准

- 用户首次进入首页时，可以仅通过文案理解记录流程，无需额外教学。
- 用户开始记录后，界面始终显示已选开始日期和当前区间预览。
- 用户在新增和编辑时，都可以反向选择日期，系统自动整理为合法区间。
- 用户离开未完成流程时，不会静默丢失输入。
- 用户在保存前即可获知区间冲突，不需要完成全部操作后才看到错误。
- 保存中不会出现仍可切月、切日期导致上下文变化的情况。

## 方案取舍

### 采用内容

- 借鉴友商“开始 / 结束分步提示”的优点。
- 保留当前单页完成记录的效率优势。
- 强化显式步骤和区间预览，降低首次使用成本。

### 不采用内容

- 不采用开关作为核心确认控件。

原因：

- `开始经期 / 结束经期` 本质是一次性提交动作，不是持续状态。
- 按钮更符合确认动作语义，能减少“当前是已开启状态还是刚完成一次操作”的歧义。

## 原则应用

- KISS：只围绕开始/结束记录交互做聚焦优化，不引入新页面和复杂向导。
- YAGNI：不借机扩展健康指标，不重做首页所有模块。
- DRY：新增和编辑统一为“选日期 + 区间预览 + 保存确认”的同一交互模型。
- SOLID：记录区面板只负责状态展示和操作引导，数据读写和预测逻辑继续留在原有模块。
